# 训练和微调必看

本文说明 `training/` 下悬疑、恐怖小说文本应如何组织、切分、加工和微调，以及最终如何服务于
`TTS-Studio-WebUI`。正式执行 Step 1–8 前应先完成本文中的数据规划。

## 核心结论

采用“统一建库、分批加工、分组切分、训练一个全局模型”的方式：

- 所有文本目录共同组成一个训练语料库，不为每个目录分别训练 LoRA。
- 人工确认故事边界时可以按目录推进，模型处理时按明确批次执行。
- 训练集、验证集、盲测集和最终测试集必须在生成教师答案前冻结。
- 同一期杂志、同一故事的转载版本、上下篇和连续系列不得跨集合。
- 当前 Step 1–8 只训练“小说原文到有声友好纯文本”，不直接训练 WebUI 剧本 JSON。

不应把整期杂志当成一条样本，也不应按固定字数随机切割故事。

## 当前文本分布

目前共有约 645 份来源 Markdown，且来源分布明显不均衡：

| 目录 | Markdown 数量 |
| --- | ---: |
| 怖客 | 265 |
| 男生女生金版 | 160 |
| 岁月推理 | 93 |
| 悚族 | 65 |
| 猛鬼杂志故事 | 52 |
| 啄木鸟 | 10 |
| 民间故事胆小鬼 | 0 |

这些数字是杂志或来源文件数量，不是完整故事数量。正式配额必须在人工确认故事边界、去重后，按
“可用完整故事数”重新计算。不能简单按当前文件数量等比例训练，否则模型容易偏向《怖客》和
《男生女生金版》的表达方式。

## 推荐流水线

```text
全部文本目录
  ↓
统一来源与故事登记库
  ↓
人工确认完整故事边界、授权状态和重复关系
  ↓
按来源、风格、长度和难度分层，按期刊/系列分组切分
  ↓
Step 2–6 分批生成、复核和人工批准 A→B 数据
  ↓
Step 8 使用全部批准训练数据训练一个全局 LoRA
  ↓
LoRA 输出有声友好文本 B
  ↓
TTS-Studio-WebUI 把 B 转为可演绎剧本 JSON
  ↓
VoxCPM2、SFX、BGM 和空间音频生成及试听
```

## 目录与批次如何处理

Step 1 应对整个 `training/` 统一生成来源清单。之后可以逐个目录人工确认边界，但最终要合并为一份
全局审核清单，例如：

```text
work/training-pipeline/boundaries.reviewed.jsonl
```

推荐的执行粒度如下：

1. Step 1 全局运行一次，建立统一故事 ID 和去重关系。
2. 人工边界审核按目录或杂志批次推进。
3. 将批准记录合并进同一份全局边界清单。
4. Step 2–6 每批处理约 100–200 篇故事，批次内尽量覆盖多个来源和难度。
5. 中间结果始终写入同一个 `work/training-pipeline/`，依靠来源哈希断点续跑。
6. Step 8 不按目录分别训练，而是在全局批准数据上训练一个 LoRA。

当前 Step 2–5 主要通过 `--include-split` 和 `--limit` 控制范围，不能保证批次来源均衡。正式全量执行
前，宜增加显式 `--batch-manifest` 或 `--include-source-prefix` 过滤能力；不要依赖 `--limit` 代替
正式批次清单。

## 数据集切分

必须同时预留验证集和最终测试集。建议比例为：

| 集合 | 建议比例 | 用途 |
| --- | ---: | --- |
| `train` | 75%–80% | LoRA 参数训练 |
| `validation` | 8%–10% | 选择 checkpoint、学习率、轮次等配置 |
| `blind` | 5%–8%，至少 60 篇 | Step 7 匿名比较和方案选择 |
| `test` | 5%–8%，至少 40 篇 | 最终版本一次性验收 |

如果第一版得到约 600 篇批准且去重后的完整故事，可采用：

```text
train       450
validation   50
blind        60
test         40
```

`blind` 用于反复比较模型或调整方案后，已经不再是真正未使用的数据，因此必须额外保留 `test`。
最终测试集在模型、Prompt、超参数和 checkpoint 全部确定前不得参与选择。

### 防止数据泄漏

切分不能只按单篇内容哈希随机进行，至少遵守以下规则：

- 同一来源 Markdown、同一期杂志中的所有故事进入同一集合。
- 同一故事的转载、改名版本和近重复版本进入同一集合，并只保留一个有效训练样本。
- 上下篇、连续系列和共享核心情节的故事进入同一集合。
- 每个集合应覆盖不同文本目录、恐惧程度、篇幅、角色数量、对白密度和叙事结构。
- 可额外建立少量“未见来源/作者”挑战集，用于检查跨风格泛化，但不能替代主测试集。

建议为每篇故事补充以下元数据，供分层与评测使用：

```text
source_collection、source_issue、canonical_story_group、series_group、year、author、
horror_level、subgenre、character_count、dialogue_ratio、length_bucket、ocr_risk
```

## 与 TTS-Studio-WebUI 的职责边界

当前 Step 1–8 训练第一阶段能力：

```text
A：清洗后的完整小说原稿
→
B：事实保真、悬念保留、适合有声朗读的纯文本
```

B 中不应出现 `speaker`、`emotion`、`control_instruction`、SFX、BGM、SSML 或 WebUI JSON。
TTS-Studio-WebUI 继续负责第二阶段：

```text
B：有声友好文本
→
C：角色、旁白、逐句正文、表演指令、停顿、SFX/BGM 和空间计划
```

第一阶段的验收目标不是“LoRA 能直接生成最终剧本”，而是验证 LoRA 输出是否比原始小说更容易让
WebUI 稳定生成忠实、完整、可演绎的剧本。

如果以后需要本地模型直接生成 WebUI JSON，应另建第二套 `script-director-lora` 数据：

```text
B：有声友好文本
→
C：TTS-Studio-WebUI 严格 JSON
```

不得把 A→B 纯文本样本和 B→C JSON 样本无标识地混入同一个训练任务。

## 长文本处理

完整故事用于全局人物、事实、线索和反转分析，但过长故事不能直接依赖模型上下文静默截断。应在
故事级分析完成后，按场景、转折、说话人和时间线自然切分为可演绎段落，并携带稳定的角色表、不可变
事实和上一段结尾上下文。

不应使用固定字数硬切，也不应通过重叠正文制造重复台词。需要重点检查：

- 输入与输出总 Token 是否超过 Step 6 和 LLaMA-Factory 的限制；
- 故事结尾和最终反转是否完整保留；
- 跨场景角色称呼、时间线和叙述视角是否一致；
- WebUI 输出是否因 JSON 过长而截断。

## 推荐实施阶段

### 阶段一：小规模校准

从所有非空来源中均衡选取约 60–120 篇故事，验证边界审核、教师 Prompt、质量门禁和 WebUI 接入。
这批数据用于修改规则，不能充当最终测试集。

### 阶段二：正式建库

冻结字段、边界规则、分组切分和审核标准后，扩展到至少约 600 篇高质量、去重且授权明确的完整故事。
按 100–200 篇一个批次执行 Step 2–6，并记录每个来源的通过率、失败类型和人工返工量。

### 阶段三：训练与选择

分别在约 250、500、1000 条批准样本规模上训练或评估 checkpoint，确认增加数据是否继续带来稳定收益。
只有通过验证集和盲测集的模型才能进入最终测试。

### 阶段四：端到端验收

在同一 WebUI 导演模型、Prompt、角色音色、VoxCPM2 参数及后期配置下比较：

1. 原始 A → WebUI → TTS，作为基线；
2. 未微调 Qwen 输出 B → WebUI → TTS；
3. LoRA 输出 B → WebUI → TTS；
4. 教师模型输出 B → WebUI → TTS，作为质量上界。

## 评测指标

### 文本层

- 剧情事实、人物关系、线索和反转是否保持；
- 悬疑恐惧程度是否被保留，而不是被统一“洗平”；
- 是否新增人物、剧情或错误因果；
- 是否适合朗读，且没有 Markdown、TTS 标签和导演指令。

### WebUI 剧本层

- JSON 解析和导入成功率；
- 角色与说话人识别准确率；
- 原文信息和有效对白覆盖率；
- 旁白是否按自然表演节拍拆分，25–45 个汉字作为软目标；
- `control_instruction`、克隆模式、停顿和非语言标签是否合法；
- SFX、BGM 和空间计划是否忠实且不过度添加。

### 音频层

- 可懂度、角色音色一致性和断句自然度；
- 恐惧、压抑、悬念和高潮是否形成可辨别的表演差异；
- 是否存在漏读、重复、角色串音、异常停顿或明显合成伪影；
- 同一角色和同一参考音频下，LoRA 流程是否稳定优于原始文本基线。

## 正式运行前必须补齐

- 将现有单篇哈希自动切分改为按来源/系列分组、按风格分层切分。
- 将验证集从默认 20 篇提高到足以覆盖来源和难度的规模。
- 自动生成并永久冻结独立 `test` 集。
- 为 Step 2–5 增加显式批次或来源过滤能力。
- 补充故事来源、强度、篇幅、对白和 OCR 风险元数据。
- 在盲测中加入“原始 A 直接进入 WebUI”的端到端基线。
- 正式训练前确认所有进入云端处理和训练的数据具有可审计授权。

在以上事项完成前，可以运行 Step 1 建立清单和开展小规模校准，但不宜直接全量执行 Step 2–8。
